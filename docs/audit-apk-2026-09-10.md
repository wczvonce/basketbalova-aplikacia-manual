# Statická analýza mobilného APK BBALL

## Podklad a hranice

Z telefónu vlastníka boli cez autorizované ADB iba skopírované inštalačné súbory balíka `sk.sotec.bball`: base APK a jazykové/hustotné doplnky. Dáta aplikácie, nastavenia a inštalácia sa nemenili. Verzia podľa manifestu: **1.0.35.0**, versionCode **61**. SHA-256 base APK: `3148E0BCDEC9C7858634A32CFFC08EC3E8A94EBEFE613E92D2F3BE15D40B5189`.

JADX 1.5.6 z oficiálneho repozitára skylot/jadx spracoval APK lokálne. Celý beh hlásil 110 dekompilačných chýb; nejde teda o úplnú obnovu pôvodného projektu. Nižšie uvedené závery sú obmedzené na čitateľné konkrétne metódy, väzby a XML zdroje. Aplikácia sa nespúšťala, API sa nevolalo. APK ani dekompilovaný kód sa do verejného manuálu nepridávajú.

Cesty nižšie sú relatívne k výstupu JADX, nie k pôvodnému C# ZIP-u. Čísla riadkov patria tomuto dekompilačnému výstupu.

## K03: Index 2241 %: zúženie miesta chyby

## K04: Mobilné WATCH nastavenie: ďalšia otvorená väzba

`SettingsViewModel.java:1463`, `saveUserParamMarkPlayerWatchPointsAverage`, vytvára WsUsrParam typu MarkPlayerWatchPointsAverage a odosiela ho cez `UserApi.saveParam`. Mobil teda obsahuje cestu používateľského parametra, zatiaľ čo dodaný serverový prepočet WATCH číta systémový parameter.

Bez serverového endpointu a jeho mapovania nemožno potvrdiť, či sa tieto hodnoty synchronizujú alebo či mobilné nastavenie ovplyvní aktuálny prepočet WATCH. Toto nie je dôkaz nefunkčnosti, ale konkrétna požiadavka na preverenie. V rámci auditu sa žiadne nastavenie nemenilo.

## K05: Mobilný JSON vzniká v telefóne

`ui/match/MatchFragment.java:149`, obsluha exportu, serializuje aktuálnu hodnotu `getMatch().getValue()` cez Gson s odsadením. Koreňom je **jeden WsStaMatch objekt, nie pole zápasov**. Export sám nevyžiada nový detail zo servera; obnovenie je samostatná akcia. Na Androide 10+ používa MediaStore Downloads, MIME application/json a UTF-8. Názov skladá z BBALL, skratiek tímov a dátumu zápasu vo formáte yyyyMMdd.

`ui/match/MatchViewModel.java:251`, `fillTeamData`, predtým dopĺňa načítaným tímom periódy, vzájomné zápasy, odvodené zoznamy hráčov a kurzy. Export preto nie je nutne nezmenenou odpoveďou API. Môže obsahovať aj klientom pripravené údaje. Nie je automaticky predzápasovou snímkou ani dôkazom historicky dostupných informácií.

Praktický postup: pred exportom detail obnoviť a počkať na úspešné načítanie. Na historické testovanie samostatne uchovať čas získania súboru a preveriť časový pôvod štatistík. Hromadný CMS export je iná cesta; jeho koreňový formát nemožno odvodiť z mobilnej obsluhy.

## K14: Mapa rozhraní a čo ešte získať od vývojára

`services/api/StatisticsApi.java` obnovuje klientsky kontrakt pre GetMatch, GetMatches, GetMatchPeriods, GetTeam/GetTeams, GetCompetition, GetRulePlayers, SaveRulePlayers, SaveCompetition, SaveTeam, UpdatePlayersBasicData a samostatné pridanie/odobratie obľúbených, kontroly a upozornení. Zápisové operácie sú POST; samotný zoznam ich názvov nie je potvrdením oprávnení servera.

Z APK už poznáme podstatnú časť mobilného zobrazovania, serializácie a požiadaviek. Na kompletný udržiavateľný projekt však stále treba:

- Pôvodný Android/Kotlin projekt vrátane Gradle konfigurácie, verzií závislostí, manifestov, resources, variantov TEST/produkcia a postupu zostavenia. Dekompilovaný Java výstup nie je jeho náhradou.
- Serverové controllery a webové DTO/mapovania, najmä GetMatch, SaveParam, ValueApi a exporty; konkrétnu API odpoveď pre chybný PairMatch index.
- Zdroj PC administrácie, jej build a nasadenie, autentifikáciu a pravidlá rolí.
- Importné dekodéry/konektory, scheduler a spúšťacie projekty; úplnú schému/migrácie databázy a dokumentáciu konfigurácie bez produkčných hesiel.
- Testy, verzie nasadených komponentov a bezpečný postup nasadenia. Prístupové tajomstvá a podpisový kľúč riešiť oddelene bezpečným odovzdaním, nie verejným repozitárom manuálu.

Najbližší užitočný dôkaz bez Petra je mobilný JSON po úspešnom obnovení konkrétneho detailu. Poskytne reálne hodnoty a štruktúru, ale nenahradí chýbajúce serverové zdroje. Na vysvetlenie bežného ovládania netreba čakať na úplný projekt; na opravu výpočtu indexu alebo serverových mapovaní áno.

## K16: Nedostatočná kontrola uloženia TOP X/Y

`ui/settings/SettingsViewModel.java:1103`, `saveMarkPlayerCountMatchesXY`, odošle zmenu len pri rozdiele oproti lokálnej starej hodnote. Metóda na riadku 1110 odosiela X aj Y v jednej požiadavke SaveParams. To nepotvrdzuje databázovú transakciu na serveri.

V obsluhe onResponse sa však staré X/Y prepíšu aktuálnymi hodnotami **pred** kontrolou úspechu HTTP. Pri úspešnom HTTP klient zobrazí hlásenie o uložení bez kontroly `WSResultModel.State`, hoci model toto pole obsahuje. Toto je konkrétny nedostatok klientského spracovania, s podmienenými dôsledkami:

- Pri HTTP 2xx s chybovým State môže vzniknúť nesprávne hlásenie úspechu. Nie je overené, či daný server takú odpoveď posiela.
- Pri neúspešnom HTTP klient síce zobrazí chybu, ale rovnaké X/Y už môžu vyzerať ako nezmenené a opakované uloženie skončí bez požiadavky, kým sa stav znovu nenačíta alebo hodnoty nezmenia.
- Pri transportnom onFailure sa v tejto metóde staré X/Y neprepisujú; nejde teda o rovnaký priebeh ako pri HTTP chybe.

Odporúčaná oprava pre vývojára: potvrdiť HTTP aj aplikačný State a až následne aktualizovať staré hodnoty; pri zamietnutí zachovať možnosť opakovania. Regresné testy: úspech, HTTP 4xx/5xx, HTTP 2xx s chybovým State a výpadok spojenia. Testovať s mock odpoveďami, nie zmenou produkčných prahov. Používateľská kontrola: po zmene obrazovku nastavení znovu otvoriť a overiť hodnotu načítanú zo servera.

## K17: Sivé nastavenie nemusí znamenať chýbajúce oprávnenie

`SettingsViewModel.java:841`, `loadUserParams`, najprv nastaví príznaky allow pre väčšinu serverových nastavení na false. Až po úspešnom HTTP a STATE_VALID ich povolí a doplní hodnoty z GetParams. Táto vetva nerozlišuje jednotlivé roly. Preto samotný neaktívny ovládač nemusí znamenať zákaz účtu; príčinou môže byť nedokončené alebo neúspešné načítanie.

Táto klientská dostupnosť zároveň nedokazuje, že server dovolí zápis každému používateľovi. Overenie oprávnení a väzby používateľských/systémových WATCH parametrov zostáva otvorené. Nenahrádzať nenačítané hodnoty odhadnutými defaultmi.

## K18: História upozornení a riziko stránkovania

`ui/notifications/NotificationListViewModel.java`, `loadItems`, získava históriu zo servera cez GetNotifications s číslom stránky. Nie je to čítanie histórie systémových bannerov Androidu. Prítomnosť záznamu v zozname preto sama nepotvrdzuje, že telefón upozornenie zobrazil alebo prehral zvuk.

Staticky zistené riziká, zatiaľ nereprodukované: loadNextPage zvýši pageIndex pred odpoveďou a onFailure ho nevracia; vetva STATE_NO_DATA vymaže celý zoznam aj bez podmienky prvej stránky. Ak server na konci histórie vráti STATE_NO_DATA, môže tým zmiznúť aj už načítaná história. Výstup dekompilácie obsahuje varovania generických typov; uvedené závery sa opierajú o samostatné čitateľné priradenia a podmienky, nie o poškodené deklarácie typov.

Test pre vývojára: stránka 1 s dátami, ďalšia prázdna stránka, chyba na druhej stránke a opakovanie požiadavky. Očakávanie: zachovať skoršie položky, ukončiť indikátor načítania a nepreskočiť neúspešnú stránku. Bez odpovedí reálneho API nemožno potvrdiť, že sa tento problém aktuálne prejavuje.

## K19: Deklarované pravidlá nie sú dôkazom dostupnej obrazovky

APK obsahuje WsStaRulePlayer, ViewSettingsRule a deklarácie GetRulePlayers/SaveRulePlayers v StatisticsApi. Vyhľadanie ich volaní v obnovenom priestore `sk/sotec` neukázalo bežného volajúceho týchto API metód. Nevyvodzujeme z toho odstránenie funkcie: časť kódu nemusí byť úplne obnovená alebo môže používať inú cestu. Manuál preto tieto deklarácie neprezentuje ako overený postup úpravy pravidiel.

Toto je dôležitá hranica auditu: existencia názvu, modelu alebo API rozhrania v APK ešte nepotvrdzuje aktívnu funkciu, povolenie používateľa ani jej serverový účinok.
